## Overview

The TeamBattles API meters requests with durable **token buckets**. Each bucket has a
fixed capacity (the burst you can spend at once) and refills at a steady rate. A
request spends one token; a batch request spends one token per item. When a bucket is
empty the request is rejected with `429`.

Three buckets apply, in this order:

1. A per-IP flood guard (before your key is even validated).
2. Your per-key request bucket.
3. A dedicated batch bucket (only on batch endpoints).

## Per-key limit

Every request you make spends one token from your key's bucket. The bucket's capacity
(your burst) and refill rate scale with your **developer plan**:

| Plan       | Capacity (burst) | Refill           | Sustained rate |
| ---------- | ---------------- | ---------------- | -------------- |
| **Free**   | 60 tokens        | 1 token/second   | ~1 req/second  |
| **Pro**    | 300 tokens       | 10 tokens/second | ~10 req/second |
| **Studio** | 1000 tokens      | 30 tokens/second | ~30 req/second |

So on the Free plan you can burst up to 60 requests, then settle into ~1 request/second
sustained; Pro and Studio raise both the burst and the sustained rate. When the bucket is
empty you receive `429 error_api_rate_limited`.

<Note>
	These ceilings are enforced per plan. A key is metered at the plan of the principal
	it acts for: a personal key uses your account's developer plan, and a league-operator
	key uses the league owner's developer plan.
</Note>

<Note>
	Enforcement is **shard-approximate at the margin**. To stay fast when many requests
	for the same key arrive at once, the per-key bucket is split into parallel shards. Your
	**sustained** rate is still enforced exactly and the advertised ceiling
	(`X-RateLimit-Limit`) is exact, but a sharp concurrent burst may be denied slightly
	before, or allowed slightly past, the exact aggregate capacity - by up to about a
	quarter of your burst. Do not treat a single `429` near the limit as an exact cutoff:
	honor `Retry-After` and retry.
</Note>

## Per-IP flood guard

Before your API key is validated, an IP-keyed bucket throttles raw request volume from a
single address. This protects the validation path from floods; it is a defensive guard,
not a per-key contract.

| Setting  | Value            |
| -------- | ---------------- |
| Capacity | 300 tokens       |
| Refill   | 50 tokens/second |

Exhausting it returns `429 error_ip_rate_limited`. If the client IP cannot be
determined the guard is skipped (it fails open). Like the per-key bucket, the flood
guard is sharded, so its cutoff is approximate at the margin under a concurrent burst
from one address; its sustained ceiling holds exactly.

## Batch endpoints

Batch endpoints (for example `POST /api/v1/game/matches/batch-scores`) charge **one
token per item** against a separate batch bucket, so a 50-item batch costs 50 tokens.

| Setting           | Value            |
| ----------------- | ---------------- |
| Capacity          | 200 tokens       |
| Refill            | 2 tokens/second  |
| Charge            | 1 token per item |
| Max items / batch | 50               |

A batch larger than 50 items is rejected with `400 error_invalid_num_items` before any
work is done. If the batch bucket is empty the response is `429 error_api_rate_limited`
(the same code as the per-key bucket). The per-key bucket is also charged on batch
routes, so a `429` there can mean either bucket was exhausted.

Unlike the per-key and per-IP buckets, the batch bucket is **exact and unsharded**: its
per-item cost accounting is not approximated at the margin.

## Response headers

Every response - both successful and rate-limited - carries:

| Header                  | Meaning                                                              |
| ----------------------- | ------------------------------------------------------------------- |
| `X-RateLimit-Limit`     | The bucket capacity. This value is exact.                            |
| `X-RateLimit-Remaining` | Estimated tokens left after this request (never negative). Because the bucket is sharded, this is an approximation, not an exact count. |
| `X-RateLimit-Reset`     | **Seconds until** the bucket has enough tokens again (not a Unix timestamp). A conservative upper bound - a retry may succeed sooner. |

On a `429` only, a `Retry-After` header is also set, with the same whole-seconds value
as `X-RateLimit-Reset`. It is a conservative upper bound: wait at most that many seconds,
then retry (a retry may succeed sooner).

## Error codes

| Code                      | HTTP | Meaning                                          |
| ------------------------- | ---- | ------------------------------------------------ |
| `error_api_rate_limited`  | 429  | Your per-key (or batch) bucket is empty, or the API shed momentary write contention from many concurrent requests on the same key. |
| `error_ip_rate_limited`   | 429  | The per-IP flood guard tripped.                  |
| `error_invalid_num_items` | 400  | Item count out of range: the 50-item ceiling on score-batch endpoints, or the `numItems` 1-100 range on match-listing endpoints. |

<Note>
	`error_api_rate_limited` can also surface a momentary contention shed: when a burst of
	requests on the same key or IP contend on the metering state, the API returns `429`
	instead of failing the request. Honor `Retry-After` and retry - a retry usually
	succeeds quickly. (This failure mode previously surfaced as a raw `500`.)
</Note>

## Monitoring your usage

The [metrics page](https://teambattles.gg/settings/developer/metrics) in your developer
settings visualizes how these buckets behave for your keys: a live burst-budget gauge
(effective tokens vs capacity for the selected key), a 7x24 heatmap of 429s, and a
bursty-vs-saturated classification of your last 48 hours. The gauge reflects your main
per-key bucket only - batch-bucket throttles are called out separately, since upgrading
your plan does not raise the fixed batch bucket. See
[Monitoring Your API Usage](/developers/metrics) for the full tour.
